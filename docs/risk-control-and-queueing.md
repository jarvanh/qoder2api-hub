# 排队信号与风控边界观察笔记

> issue #158 报告：所有账号在 `cn` / `intl` 均持续出现 `10605`、`queueType:p4`、`serviceAvailable:true`。这是待核实的排队现象，**原因未确认**。本文区分上游信号、进程内观察与根因，不把排队直接归因为容量、账号或网络。

## 1. 信号能说明什么

| 信号 | 可确认的事实 | 不能据此确认 |
|---|---|---|
| `10605` / `isQueued:true` / `RESOURCE_LIMIT` | 上游返回排队信号；需要结合实际响应信封或 SSE 事件解析 | 一定是模型容量不足、所有账号共享同一队列、账号/凭证/网络一定无问题 |
| `queueType:p4` / `queueType:p3` | 上游提供了队列类型标签 | 标签的公开含义、优先级、风险等级或标签之间的排序；这些语义未获文档或支持确认 |
| `serviceAvailable:true` | 本次上游队列载荷中的可用性标志为真 | 当前请求已获准推理、不会继续排队，或账号未受策略限制 |
| `serviceAvailable:false` | 本次可用性标志为假 | 唯一原因是容量不足 |
| `retryAfterSeconds` / `queueCount` | 本次上游建议的等待秒数 / 队列计数（若提供） | 一定能在该时间后成功、计数涵盖所有用户或是准确剩余名次 |
| `identity_source` | 本地身份生成路径（`native` / `derived` / `unknown`） | 上游认可该身份、是否被风控、账号是否正常 |

账号、模型、端点、套餐权限、客户端版本、请求内容、出口网络及上游调度策略都是排查维度，不是已证实的原因。多个账号或两个区域出现相同现象，也不足以排除这些维度。住宅 IP、切换区域、换号或调整请求头均没有已证实的恢复保证；不应作为绕过策略。

## 2. 进程内排队观察

`queue_observation_snapshot()` 通过公开的 `GET /health` 字段 `queue_observation` 提供安全聚合；读取健康状态不主动请求上游。它记录网关实际处理到的排队观察，不是上游全局状态，也不是独立根因检测器。

- **内部作用域**：实际使用的账号 + 实际选中的推理网关 URL（含备用主机） + 实际模型键（modelKey），内部以 SHA256 摘要作为键。不能用请求预选账号代替实际账号；不同账号、端点、模型的样本不能拼接成一次持续排队。
- **持续判据**：同一作用域至少 3 次排队观察，首末跨度至少 900 秒，相邻观察最大间隔不超过 900 秒。超过间隔的样本不应被解释成连续观测。
- **恢复判据**：只有上游成功终止帧才重置匹配的账号、端点、模型作用域，HTTP 200 握手不算成功；一个账号或模型成功，不代表其他作用域恢复。
- **存储边界**：最多 256 个作用域条目、24 小时 TTL、仅保存在当前进程内。条目过期或容量淘汰会丢失观察；重启会清空。它不能证明重启前、进程未观察期间或完整 24 小时内的历史状态。
- **公开边界**：只发布计数、时间/持续状态等允许的聚合，根因保持 `reason:unknown`。不发布原始队列文本、账号标识、端点 URL、请求/会话标识、提示词或凭证。

快照只统计最近一次观察距现在不超过 900 秒的活跃作用域；超过这个间隔即不计入活跃/持续聚合，下一次观察重新开始序列。持续标志表示“满足本地采样阈值”，不是持续每秒排队的证明，不是风险等级，也不是容量故障诊断。低频采样可能不足以触发；`persistent=false` 或空快照不能证明上游已恢复。

## 3. 一次最小诊断

`POST /diag/queue` 需要面板鉴权，会实际发出**一次上游探测**；不是只读健康检查，不宜定时高频调用。诊断消费实际 SSE，通过聚合解析器识别流内排队信封，而不是只根据 HTTP 200 或读取一段字节就判成功。

```bash
curl -sS -X POST 'http://HOST/diag/queue' \
  -H 'Content-Type: application/json' -H 'X-Panel-Token: TOKEN' \
  -d '{"uid":"TARGET","model":"TARGET","realm":"cn"}'
```

关注解析字段 `queue_type`、`service_available`、`retry_after`、`queue_count`，以及 `kind` / `reason`。缺失/无效的数值与可用性字段保留为空，队列标签为 `unknown`，不补造数值；排队根因是 `unknown`。诊断响应不提供原始队列文本。一次探测不证明持续排队，也不自动对所有账号、模型、端点或另一区域作结论。完整接口说明见 [接口参考](<api.md#排队诊断post-diagqueue面板鉴权>)。

普通推理强制选区使用 `X-Realm: cn|intl` 或 URL 查询参数 `?realm=cn|intl`，**不要用推理 JSON 的 `realm` 字段作为路由依据**。`/diag/queue` 的 JSON `realm` 是诊断处理器显式支持的单独参数；普通推理并不因此支持。应核对响应 `X-Qoder-Realm`、`X-Qoder-Realm-Reason`，并注意 Key 的区域绑定优先级。

## 4. 受控官方客户端对照

1. 先停止自动重试与并发压测，记录 UTC 时间、实际账号（只在本地/支持渠道保留）、套餐、区域、明确模型、实际端点、客户端/网关版本和网络环境。将请求压到一个短文本、无工具、无图片的最小样本。
2. 在**同一账号、同一时间窗口、同一区域、同一明确模型**下，对比官方客户端与网关。保持出口和输入等其他变量一致，顺序执行而非制造并发；记录各自请求起止时间，避免把不同负载时段当作同一时刻。无法对齐端点或模型别名时明确记录差异。
3. 每次排队后尊重上游 `retryAfterSeconds` / HTTP `Retry-After`，到达有限重试次数或总等待预算就停止，不循环探测所有账号，不无限重试。需要下一组样本时在等待窗口后再执行。
4. 两边都排队仅支持“同一窗口有共同现象”；只有网关排队仅支持“客户端路径存在差异”。两者均不直接确认容量或风控。
5. 若持续出现，将脱敏的时间线、版本、区域/模型、结构化排队字段、对照结果交官方支持，要求确认队列标签含义、账号/套餐资格、策略限制与服务状态。没有支持确认前保持 `reason=unknown`；不要上传 token、机器身份材料、完整提示词或原始响应文本。

## 5. 本地调度能控制的边界

| 机制 | 当前行为与限制 |
|---|---|
| `QD_TRAFFIC_GUARD=on` | 让所有账号进入现有按账号闸门；不是进程全局/IP 全局限流器 |
| `QD_TEAM_MAX_CONCURRENCY` / `QD_TEAM_MIN_GAP_MS` | 默认每账号并发 1 / 最小间隔 400ms；这是本地整形设置，不是上游承诺 |
| `QD_TEAM_WAIT_SECS` | 等租约默认 30 秒，超时 **fail-open**，会不持有租约继续；异常路径也可能放行，因此不是严格并发保证 |
| 守卫未设置 / `off` | 未设置保留原有团队账号判定；`off` 关闭守卫。本文不调整默认值 |
| `QD_QUEUE_WAIT_MODE` | 默认 `visible`，流式报告排队进度；`fast` 快速返回带 `Retry-After` 的 503；`wait` 是兼容的静默等待模式 |
| `QD_QUEUE_*` | 当前默认 `QD_QUEUE_MAX_ROUNDS=3`、`QD_QUEUE_WAIT_MAX_SECS=180`、`QD_QUEUE_WAIT_BUDGET_SECS=600`、`QD_QUEUE_WAIT_JITTER=2`；各等待路径受各自轮次/总预算约束，不保证一定成功 |

可减少无意义请求、限制客户端并发和输出长度、控制请求体积、避免客户端与网关叠加重试，但这些只是本地负载管理，不是风控修复。不要为持续排队增加无限等待、轮换身份/账号/出口或绕过限制。已有默认值保持不变；先收集证据再决定正常业务的有限等待策略。

## 6. 快速判读

```text
10605 / isQueued -> 排队已确认，根因 unknown
p4 / p3          -> 未文档化标签，不映射风险等级
serviceAvailable -> 保留原值，不覆盖 queued 判定
持续排队          -> 检查同作用域样本阈值、间隔和进程生存期
Retry-After       -> 等待建议 + 有限预算，到限停止
恢复              -> 仅清理匹配作用域，不清全局
官方客户端对照     -> 同账号 / 同时间窗口 / 同模型 / 同区域
根因确认           -> 官方支持，不由标签或网络类型推定
```
