# 持续排队排查手册（cn / intl）

> issue #158 的“所有账号、两个区域持续 `10605` / `p4` / `serviceAvailable:true`”是待确认的现象，不是容量故障或账号受限的既定结论。本手册用于有限采样、受控对照与支持确认，不提供绕过方案。

## 1. 先固定证据口径

- `10605` / `isQueued:true` 表示收到排队信号；不证明仅由模型容量导致，也不证明账号、凭证、套餐、网络无问题。
- `p4` / `p3` 的公开语义未确认，不把它们排序为风险等级或优先级。
- `serviceAvailable:true` 与排队可以同时出现，不能用来覆盖 `queued` 或宣称请求已经放行。
- 出口 IP/ASN、客户端身份、请求行为、端点、模型、账号资格都是待核对变量。没有出口影响占比的可靠测量依据，也没有“住宅出口必定恢复”的保证。
- 原因未确认时统一写 `reason=unknown`。任何改动前保留当前配置；本次排查不修改守卫或等待默认值。

## 2. 先看本地观察，不主动刷探测

```bash
# 公开聚合；读取不会发上游探测
curl -sS 'http://HOST/health'
```

关注 `risk` 与 `queue_observation`，不要把两者混为一谈：前者是信号计数，后者来自 `queue_observation_snapshot()`，用于区分观察不足、短时与满足本地持续判据的排队。

| 项目 | 精确边界 |
|---|---|
| 内部作用域 | 实际账号 + 实际端点域名 + 实际模型键（modelKey）；不会把不同作用域样本混合 |
| 持续阈值 | 同作用域至少 3 次排队观察，首末跨度至少 900 秒，相邻最大间隔不超过 900 秒 |
| 成功重置 | 上游成功终止帧只重置匹配作用域；HTTP 200 握手不算成功，不以其他账号/模型成功清空全部状态 |
| 容量 / 生命周期 | 最多 256 个作用域条目，TTL 24 小时，当前进程内存；重启清空，过期/淘汰丢失观察 |
| 公开输出 | 安全聚合和 `reason:unknown`；无原始队列文本、账号 ID、实际端点、凭证、请求标识或提示词 |

快照只统计最后一次观察距现在不超过 900 秒的活跃作用域，间隔超出即不计入活跃/持续聚合，下一次观察重新起算。这不是跨重启历史记录。没有观测不等于没有排队，满足持续阈值也不证明两次采样之间每秒都在排队。多个账号、端点或模型的单次样本不能累加成一个作用域的“持续排队”。

## 3. 有需要时只做一次最小探测

```bash
curl -sS -X POST 'http://HOST/diag/queue' \
  -H 'Content-Type: application/json' -H 'X-Panel-Token: TOKEN' \
  -d '{"uid":"TARGET","model":"TARGET","realm":"intl"}'
```

- 需要面板会话；`uid` / `model` 使用待核对的实际对象。`realm` 在这个诊断接口中由 JSON 显式支持。
- 每次调用只发一个上游探测，并通过聚合解析器消费实际 SSE；HTTP 200 本身不代表推理成功。
- 记录 `kind`、`queue_type`、`service_available`、`retry_after`、`queue_count` 与 `reason`；缺失/无效的数值与可用性字段保持为空，队列标签为 `unknown`，不回传原始队列文本。
- 诊断会产生上游请求，不用作高频健康检查；不要轮流刷全账号池来积累“持续”样本。
- 普通推理的强制选区仅用 `X-Realm: cn|intl` 或 `?realm=cn|intl`，推理 JSON 的 `realm` 不参与普通路由。Key 的区域绑定可能优先，应核对 `X-Qoder-Realm` 和 `X-Qoder-Realm-Reason`。

详见 [接口参考](<api.md#排队诊断post-diagqueue面板鉴权>)。

## 4. 官方客户端受控对照

| 步骤 | 操作与记录 |
|---|---|
| 固定变量 | 同一账号、套餐、区域、明确模型、短文本输入、出口与时间窗口；记录官方客户端/网关版本和实际端点 |
| 排除自造并发 | 停掉其他客户端自动重试，逐次测试，不同时打两个请求；记录起止时间与不能对齐的变量 |
| 对比结果 | 官方客户端与网关分别记录成功/排队/其他错误及结构化字段；不要根据官方 UI 没显示队列就假定它没排队 |
| 尊重等待 | 遵守 `retryAfterSeconds` / `Retry-After`，设有限次数、总时间预算；到限停止，保留结果 |
| 解释差异 | 同时排队说明共同现象；仅网关排队说明路径差异；均不足以确认具体策略或容量原因 |
| 官方确认 | 交支持核对队列类型含义、账号/套餐资格、服务状态、端点/版本与策略限制；确认前 `reason=unknown` |

支持材料模板（本地填入实际值，对外仅保留必要脱敏信息）：

```text
时间窗口（UTC）: TARGET
区域 / 模型 / 实际端点: TARGET
官方客户端版本 / 网关版本: TARGET
同账号同时间窗口对照: TARGET
kind / code / queue_type / service_available: TARGET
retry_after / queue_count: TARGET
本地观察次数 / 首末跨度 / 最大间隔: TARGET
当前进程启动时间 / 是否重启或有样本缺口: TARGET
期望支持确认: 标签含义、账号资格、服务状态、策略原因
当前结论: reason=unknown
```

不要提交 token、机器身份材料、原始队列文本或完整提示词。支持确认应作为新的证据单独记录，不倒推历史样本的根因。

## 5. 现有守卫不是全局限流保证

| 设置 | 当前实现 |
|---|---|
| `QD_TRAFFIC_GUARD=on` | 所有账号走现有按账号闸门；不是全进程、全账号池或出口 IP 共享限流器 |
| `QD_TEAM_MAX_CONCURRENCY` | 默认每账号并发 1 |
| `QD_TEAM_MIN_GAP_MS` | 默认每账号最小间隔 400ms |
| `QD_TEAM_WAIT_SECS` | 默认等租约 30 秒，超时 fail-open、不持租约继续请求；异常也可能放行，因此不是严格上限 |
| 守卫未设置 / `off` | 未设置保留旧的团队账号判定，`off` 关闭；不修改默认值 |

本地守卫只能减少特定路径上的并发/突发，不能确认或清除上游风险策略；不保证消除排队。不同进程/实例的守卫和观察不共享，也不能据单实例状态推断全局流量。

## 6. 等待与停止条件

- `QD_QUEUE_WAIT_MODE=visible` 是当前默认，流式报告进度；`fast` 快速返回带 `Retry-After` 的 503；`wait` 保留静默等待兼容路径。不要把模式切换当成恢复上游服务。
- 当前等待配置默认：`QD_QUEUE_MAX_ROUNDS=3`、`QD_QUEUE_WAIT_MAX_SECS=180`、`QD_QUEUE_WAIT_BUDGET_SECS=600`、`QD_QUEUE_WAIT_JITTER=2`。不同路径受各自轮次/总预算控制；本文不提高这些值。
- 排队后尊重上游建议等待，避免网关和 SDK 各自多层重试；总预算或次数耗尽即停止，记录最终状态，不无穷重开流。
- 若有明确的凭证过期、套餐权限或版本门错误，按该错误分别核对授权、资格或升级；不要把所有 403、429 或 10605 归为同一种原因。
- 验收以事实为准：解析字段正确、作用域隔离、有限重试、成功只重置匹配作用域、公开输出无敏感信息。没有经测量的成功率目标，不承诺固定排队率或更换网络后的成功率。

进一步的信号解释与实现边界见 [排队观察笔记](<risk-control-and-queueing.md>)。
